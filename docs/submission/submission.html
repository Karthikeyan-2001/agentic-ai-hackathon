1. The problem and our idea

Generic AI tutors answer questions, but they don't track what a student actually understands. Most quiz tools also look only at the final answer. Yet the same wrong answer can come from completely different misunderstandings, and a right answer can hide a wrong belief that will break on the next problem.

Differential is a Class 10 Python Programming tutor that reads the student's reasoning, not just the answer. Its name comes from a doctor's differential diagnosis: when a student makes a mistake, it forms competing explanations, then asks the question that best separates them.

One question, three students, three different problems

Every student is asked: "How many times does the body of for i in range(1, 5): run?" (Correct answer: 4 times.)

StudentAnswerTheir reasoningDifferential's diagnosisMasteryNext question tests
A5 times Wrong"It counts up to and including 5"Thinks range includes its stop valueFallsThe last number printed by range(3, 7)
B5 times Wrong"The 5 says how many times"Thinks the stop value is the number of repeatsFallsHow many times range(4, 6) runs
C4 times Right"It is always one less than the stop number"Right answer, wrong reasonUnchangedHow many times range(3, 8) runs

An answer-only tutor treats A and B the same and gives C full marks. Differential gives A and B different diagnoses and different follow-up questions, and it gives C no credit until the reasoning holds up on a loop that doesn't start at 1.

Our main design rule: the LLM interprets and the code decides. The language model only reads the student's reasoning and returns structured data. Tested, deterministic code marks every answer, changes every score and chooses every question. Code written by the LLM is never run. This makes every number on screen explainable and testable.

Beyond the brief

  • Separating explanations: when two misconceptions are both possible, code picks the question whose options split them apart, like a doctor ordering the test that rules one out.
  • "Right answer, wrong reason": a correct answer with flawed reasoning earns no mastery.
  • Thinking panel: the student sees the explanations the tutor is weighing and why it chose the next question.
  • Root causes: the dashboard traces low scores back to the earliest weak prerequisite behind them.
  • Fully local and private: the model runs on the team's own PC, so the tutor works offline.
  • Measured accuracy on held-out test cases, reported honestly (section 11).

4. What happens on every answer

This is the core flow of the product. Each time a student submits an answer, the agent loop runs six steps. Only one of them uses the LLM.

Step by step

  1. Check. Each option in the question bank has an is_correct flag. Code compares the student's option. The LLM never marks answers.
  2. Diagnose. The local LLM receives the question, the chosen option, whether it was correct, the student's reasoning and the misconception catalogue. It returns JSON matching a fixed schema: error_type, misconception_id, first_wrong_step, evidence_quote and confidence.
  3. Validate. Code rejects anything it can't verify: the quote must appear in the student's text, the misconception ID must be in the catalogue, and diagnoses below 60% confidence are treated as "unclear".
  4. Update. The engine updates concept mastery (section 5), spreads the change to prerequisites, updates each misconception's probability, reschedules reviews (section 8) and updates Elo ratings for the student and the question.
  5. Decide. The engine chooses the next question with fixed priority rules (section 7).
  6. Explain. The response carries a trace: the explanations being weighed, their probabilities and why the next question was chosen. The student sees this in the "What the agent is thinking" panel.

Answer response (from POST /api/students/{id}/answers)

FieldMeaning
correctWhether the chosen option was right (set by code)
diagnosisThe validated error type, misconception and quoted evidence
diagnosis_statusok, cached or failed, so the UI is honest about where the diagnosis came from
mastery_changes, misconception_changesBefore and after values, shown on the result card

5. The learner model

For each student, the learner model holds a mastery value for every concept and a probability for every misconception. Both update after every answer. All functions are pure and take the current time as an argument.

5.1 Mastery: Bayesian Knowledge Tracing that listens to the reasoning

Each concept starts at mastery 0.30 and stays between 0.01 and 0.99. The update uses standard Bayesian Knowledge Tracing:

Correct:  p' = p(1-s) / ( p(1-s) + (1-p)g )
Wrong:    p' = p·s   / ( p·s    + (1-p)(1-g) )
Learning: p'' = p' + (1-p')·T

The key idea is that the slip (s), guess (g) and learn (T) values depend on the diagnosis, not just on right or wrong:

AnswerDiagnosis (error_type)sgTStarting from 0.5Meaning
Correctnone (sound reasoning)0.10.20.10.836Real understanding: mastery rises
Correctmisconception, gap0.10.900.500Right for the wrong reason: no credit
Correctslip, unclear0.10.500.643Partial credit
Wrongmisconception, gap, none, unclear0.10.200.111Mastery falls
Wrongslip (careless error)0.60.200.429Barely lowered

5.2 Spreading along the concept graph

A mastery change of d also moves the concept's prerequisites, up to two links back: by d × 0.3 per link when it rises, and d × 0.1 per link when it falls. Failing "Nested loops" is mild evidence of weakness in "for loops with range", but succeeding at it is stronger evidence of strength.

5.3 Misconception probabilities

Each misconception starts at probability 0.05. The confidence tap sets a multiplier k: 1.0 for "Sure", 0.6 for "Not sure".

EventUpdate
Diagnosis names misconception m with confidence c ≥ 0.6p += (1-p) × 0.7 × c × k
The chosen option maps to m, but the diagnosis didn't name itp += (1-p) × 0.2 × k
Correct answer with sound reasoning on a question that has an option for mp × 0.5

Status follows the probability: inactive below 0.2 → candidate 0.2–0.5 → active 0.5 and above → resolved when an active one falls below 0.2. A resolved misconception that climbs back to 0.5 becomes active again.

5.4 Difficulty calibration with Elo

Each student starts at 1500 Elo. Each question starts from its difficulty prior (1 → 1200, 2 → 1350, 3 → 1500, 4 → 1650, 5 → 1800). Expected success is E = 1 / (1 + 10^((d − a)/400)), and after each answer both ratings move by 32 × (actual − E). The dashboard flags a question when its rating has moved 150 or more from its prior after at least 10 attempts, so teachers can see questions that are harder or easier than expected.

6. Misconception detection from reasoning

The brief asked for misconceptions to be detected from the reasoning in wrong answers, not just the wrong final answer. Differential does this in two layers: the local LLM reads the explanation, and code checks the LLM's work.

6.1 The misconception catalogue (Python Programming)

IDThe student believes…
range_includes_stoprange(start, stop) includes the stop value, so the loop reaches that number
range_stop_is_countThe stop value says how many times the loop runs, whatever the start value is
range_one_less_than_stopA loop always runs one less time than its stop value, ignoring the start value
assignment_links_variablesb = a links the two variables, so changing a later also changes b
integer_division_rounds// rounds to the nearest whole number instead of dropping the part after the decimal point
string_plus_adds+ adds digits as numbers even when they are strings in quotes
while_exits_mid_bodyA while loop stops the moment its condition becomes false, skipping the rest of the body
index_starts_at_oneList indexes start at 1, so index 1 is the first item

Each question option is mapped to the misconceptions that would lead a student to pick it. One option can map to several misconceptions, which is exactly why reading the reasoning matters: Students A and B pick the same option for different reasons.

6.2 Error types

error_typeMeaning

slipThe reasoning is sound, with a careless or calculation error
gapThe student doesn't know, or guessed
unclearThe reasoning can't be judged from the text

6.3 How code keeps the LLM honest

Evidence must be real

The LLM must quote the student's own words. If the quote doesn't appear in the student's text, code removes it and caps the confidence at 0.5.

Uncertain means ask again

A diagnosis below 0.6 confidence is treated as "unclear". The tutor then asks another question instead of asserting a misconception.

Fixed vocabulary

The reply must match a Pydantic JSON schema, and the misconception ID must come from the catalogue. Invalid replies are retried up to two times.

Student text is untrusted

Reasoning is wrapped in clear delimiters and the prompt treats it only as data, so a student can't instruct the model. Empty reasoning skips the LLM.

7. Choosing and generating questions

After every answer, code applies the first rule in this list that returns a question. The student's three most recent questions are always excluded.

7.1 Separating explanations

When two misconceptions are both plausible, every available question gets a score:

score = sum of p(m) for each of the top-two misconceptions that has an option in the question
        + 0.5 if both have options and those options are different

The highest score wins. A question where the two beliefs lead to different wrong answers tells them apart in one step. For Student A, "What is the last number printed by range(3, 7)?" separates "includes the stop" from "stop is the count".

7.2 Generating questions safely

When a weak concept runs out of unseen questions, the agent can generate a new one. To avoid wrong answer keys, the LLM never writes the code or the answer:

  1. Code chooses a template from a fixed list in agent/solvers.py: floor division, modulo, powers, running totals with range, nested-loop counts and list totals.
  2. Code writes the Python program from that template and works out the correct result itself.
  3. The LLM writes only the question wording and the answer options, naming the misconception behind each wrong option.
  4. Code rejects the question unless exactly one option matches the computed answer, all options differ, every misconception ID is in the catalogue and the wording matches the numbers used. Rejected questions are retried up to two times.

scripts/pregenerate.py builds a pool of 20 checked questions ahead of time, so the demo doesn't wait on generation. LLM-written code is never run.

8. Spaced repetition

Knowledge fades. Differential models this with a forgetting curve for every concept and for every misconception the student has cleared.

Recall R = exp( −days since last practice / S )        review due when R < 0.85
Displayed mastery = mastery × (0.5 + 0.5·R)

Concept stability S

  • Starts at 2 days
  • Correct with sound reasoning: doubles
  • Slip or unclear: unchanged
  • Anything else: halves (minimum 1 day)

Cleared misconceptions

  • Start with S = 3 days once resolved
  • Rechecked when recall drops below 85%
  • A sound answer on the recheck doubles S
  • A failed recheck raises the probability again
  • Reviews always use a question the student hasn't seen recently, never the same question again.
  • All time-based calculations use an app clock with an offset. The teacher's Jump 7 days button adds a week, so the demo can show reviews coming due without waiting.

How the simulated class is built

scripts/seed_class.py creates 30 students with a fixed random seed. Each has up to two hidden misconceptions and gets 12 to 15 scripted answers. When a question has an option for a hidden misconception, the student picks it 80% of the time; otherwise they answer correctly with the probability Elo predicts. Every answer goes through the real engine, without LLM calls. This data shows how the dashboard works. It isn't evidence that diagnosis works; that comes from the evaluation in section 11.

11. Evaluation and testing

11.1 Diagnosis accuracy

We wrote 40 labelled reasoning samples as test cases. We used 10 to tune the prompt and held out 30, which were used only for the reported result. scripts/evaluate.py runs them against the local model and saves results to eval/results.json.

Measure (30 held-out cases)Thinking off (used)Thinking on
Error type correct30 of 30 (100%)30 of 30 (100%)
Misconception identified, where one was expected18 of 18 (100%)18 of 18 (100%)
Average time per diagnosis0.84 seconds3.84 seconds

Turning the model's thinking mode on gave the same accuracy at about 4.5 times the time, so we kept it off. All 8 misconceptions were covered in the held-out set.

Being honest about this result. These are written test cases, not real student data. The same AI assistant that helped write the misconception catalogue also wrote the test cases, in fairly clear wording. Real students will be harder to read, so we treat this as a check that the system works, not as evidence of accuracy with real students.

11.3 Reliability for the demo

  • Every LLM reply is cached by a hash of the model, prompt and schema. scripts/warm_demo.py runs the scripted demo answers through the real model beforehand, so the demo keeps working even if Ollama stops. It fails loudly if the tutor stops following the script.
  • The UI shows the diagnosis status (ok, cached or failed), so it never hides where a result came from.

13. Running the project

You need Python 3.12 or later, Node 20 or later, and Ollama running locally. The commands below are for Windows; on macOS or Linux use .venv/bin instead of .venv/Scripts.

Set up once

ollama pull qwen3.5:9b
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt
npm --prefix web install
npm --prefix web run build

Run

.venv/Scripts/python -m scripts.seed_class      # creates the simulated class of 30
.venv/Scripts/python -m scripts.warm_demo       # caches the demo answers
.venv/Scripts/python -m uvicorn api.main:app --port 8000

Then open http://localhost:8000 and click Start guided demo, or sign in with a demo account.

14. Limits and next steps

Current limits

  • Questions cover Python Programming only. Computer Networks, Web Pages with HTML and Cyber Ethics appear in the graph as "not assessed".
  • Comparison and logic, if and else, and functions have no questions yet.
  • New questions can be generated for arithmetic, running totals, nested loops and list traversal only. Other concepts cycle through their existing questions.
  • Sign-in is mock (passwords in code, sessions in memory). This is a local demo and shouldn't be exposed to the internet as it is.
  • No real student has used it yet, and the accuracy figure comes from written test cases.
  • The AI-written lesson plan is a draft for a teacher to review.

Next steps

  1. Real classroom pilot: test with Class 10 students and teachers, and measure diagnosis accuracy on real reasoning.
  2. Wider content: questions and misconceptions for the remaining Python concepts, then the other chapters and other subjects such as Class 10 physics.
  3. More templates so more concepts can get safely generated questions.
  4. Real accounts with several classes and teachers.
  5. Teaching impact: let teachers record "I taught this" and see the class before and after.
  6. Handwritten working: let students upload a photo of their reasoning.

Summary

Differential meets all seven requirements of the brief in one running app. What sets it apart is that it diagnoses why a student is wrong from their own words, treats a right answer with wrong reasoning as no evidence of mastery, and chooses the question that best separates competing explanations. Throughout, the LLM only interprets and tested code makes every decision, and everything runs locally on one PC.
