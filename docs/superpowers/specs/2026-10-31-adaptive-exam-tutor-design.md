# Adaptive Exam Prep Tutor: Design Spec

- **Date:** 2026-10-31
- **Working name:** Differential (from "differential diagnosis")
- **Build window:** 6 hours
- **Status:** Draft for team review

> **Topic change:** the tutor now covers Class 10 computer science, assessing Python Programming instead of Electricity. This spec still describes the original physics content, but its design is unchanged. The one exception is generated questions: code now writes the program from a fixed template and the LLM supplies only the question wording and options. `content/` and `README.md` show the current topic.

## 1. Goal

A generic AI tutor answers questions but doesn't track what a student actually understands. This project builds a tutor for Class 10 physics that works like a doctor: it forms competing explanations for a student's mistake, then asks the question that best separates them.

### Success criteria

1. All seven hackathon requirements work in the running app (section 3).
2. The three-student demo (section 2) works every time, with or without internet.
3. A measured diagnosis accuracy figure, from test cases not used for tuning, is ready for the pitch.

## 2. The demo that defines the project

Three students answer the same question:

> Two bulbs are in series. The current through the first is 0.5 A. What is the current through the second?

| Student | Answer | Reasoning | Expected diagnosis | Mastery | Next question probes |
|---|---|---|---|---|---|
| A | 0.25 A | "The first bulb used up half" | `current_consumed` | Falls | Whether the current leaving a bulb equals the current entering it |
| B | 0.25 A | "The current splits between them" | `series_parallel_confusion` | Falls | The same bulbs in series and in parallel |
| C | 0.5 A | "The bulbs are identical" | `identical_implies_equal` | Unchanged | The same circuit with two different bulbs |

A and B give the same wrong answer but get different diagnoses. C is correct but gets no credit for it.

### 3-minute demo order

1. Students A, B and C, with the agent's thinking panel visible (90 seconds).
2. A correct answer clears a misconception, then "jump 7 days" brings a review due (30 seconds).
3. Teacher dashboard: gaps, shared misconceptions and root causes (40 seconds).
4. Accuracy result and how it was measured (20 seconds).

## 3. Requirements and how they are met

| Requirement | Design |
|---|---|
| Diagnostic test | 8 adaptive questions, each with reasoning and a confidence tap (section 8.1) |
| Concept graph | About 30 concepts across Class 10 physics, with prerequisite links (section 6.1) |
| Learner model | Mastery per concept and a probability per misconception, updated after every answer (section 7) |
| Targeted question generation with calibration | Questions chosen by code and generated with checked answers (sections 8, 9); Elo calibration from class responses (section 7.5) |
| Misconception detection from reasoning | LLM matches reasoning to a catalogue and returns structured evidence (section 9.1) |
| Spaced repetition | Forgetting curve per concept and per resolved misconception (section 7.4) |
| Teacher dashboard | Heatmap, misconception groups, root causes, calibration flags and a lesson plan (section 11) |

## 5. Architecture

**Main rule: the LLM interprets and the code decides.** The LLM reads reasoning and returns structured data. Tested code changes every score and chooses every question.

```text
React app  ->  FastAPI  ->  agent loop  ->  llm.py  ->  Ollama (qwen3.5:9b)
                               |
                               +-> engine (pure functions)
                               +-> SQLite, content JSON
```

Each answer follows this loop:

1. **Check:** code marks the selected option right or wrong.
2. **Diagnose:** the LLM classifies the reasoning.
3. **Validate:** code checks the diagnosis against the catalogue and the student's text.
4. **Update:** the engine updates mastery, misconceptions, schedule and Elo.
5. **Decide:** code chooses the next question.
6. **Explain:** the response carries a trace for the thinking panel.

### Technology

| Layer | Choice |
|---|---|
| Backend | Python, FastAPI, `uvicorn[standard]`, SQLModel on SQLite, `python-dotenv` |
| LLM | `ollama` package, Pydantic schemas |
| Frontend | React with Vite and TypeScript, Tailwind, `react-router-dom`, `recharts`, `@xyflow/react`, `@dagrejs/dagre` |
| Tests | `pytest`, `httpx` |

FastAPI serves the built React app, so there is one service to run.

### Folder layout and ownership

```text
content/    concepts.json, misconceptions.json, questions.json, eval_samples.json
engine/     mastery.py, misconceptions.py, scheduling.py, elo.py, graph.py, selection.py
```

## 6. Data formats

### 6.1 `content/concepts.json`

```json
{"id": "series_current", "name": "Current in a series circuit", "chapter": "Electricity",
 "description": "The same current flows through every component in series.",
 "prerequisites": ["electric_current"]}
```

About 30 concepts, about 12 of them in Electricity. The graph must not contain cycles, and a test enforces this. Planned chapters are Light, the Human Eye, Electricity and Magnetic Effects (see section 16).

### 6.2 `content/misconceptions.json`

```json
{"id": "current_consumed", "concept_id": "series_current",
 "description": "Believes a component uses up current.",
 "example_wordings": ["the first bulb used up half"]}
```

Planned catalogue, subject to physics review:

| ID | Belief |
|---|---|
| `current_consumed` | A component uses up current |
| `series_parallel_confusion` | Current splits between components in series |
| `identical_implies_equal` | Currents are equal only because the components are identical |
| `parallel_resistance_adds` | Adding a resistor in parallel raises total resistance |
| `voltage_is_current` | Voltage and current are the same thing |
| `battery_constant_current` | A battery delivers the same current in any circuit |
| `resistance_always_brighter` | More resistance always means more power, ignoring what stays fixed |
| `thicker_wire_more_resistance` | A thicker wire has more resistance |

### 6.3 `content/questions.json`

```json
{"id": "q_series_two_bulbs", "concept_id": "series_current",
 "stem": "Two bulbs are in series. The current through the first is 0.5 A. What is the current through the second?",
 "options": [
   {"id": "a", "text": "0.25 A", "is_correct": false,
    "misconception_ids": ["current_consumed", "series_parallel_confusion"]},
   {"id": "b", "text": "0.5 A", "is_correct": true, "misconception_ids": []}
 ],
 "difficulty_prior": 2, "source": "seed"}
```

- An option may map to several misconceptions. The demo depends on this.
- `difficulty_prior` runs from 1 to 5.
- `source` is `seed` or `generated`.
- A test enforces exactly one correct option per question and valid misconception IDs.

The content set is 12 hand-checked seed questions, including the demo question and its three follow-ups, plus at least 20 generated numeric questions created ahead of time.

### 6.4 Diagnosis returned by the LLM

```python
class Diagnosis(BaseModel):
    error_type: Literal["none", "misconception", "slip", "gap", "unclear"]
    misconception_id: Literal[...catalogue IDs...] | None
    first_wrong_step: str | None
    evidence_quote: str | None
    confidence: float  # 0 to 1
```

| `error_type` | Meaning |
|---|---|
| `none` | Reasoning is sound |
| `misconception` | Reasoning shows a catalogued false belief |
| `slip` | Reasoning is sound, with a calculation or careless error |
| `gap` | Student doesn't know, or guessed |
| `unclear` | Can't be judged from the text |

The catalogue IDs are generated from `misconceptions.json` when the app starts.

### 6.5 Database tables

| Table | Key fields |
|---|---|
| `student` | id, name, is_simulated, ability_elo, pinned_question_id, diagnostic_complete |
| `concept_state` | student_id, concept_id, mastery, stability_days, last_practiced_at |
| `misconception_state` | student_id, misconception_id, probability, status, stability_days, resolved_at |
| `answer` | student_id, question_id, option_id, reasoning, confidence_tap, diagnosis_json, trace_json, created_at |
| `question_state` | question_id, difficulty_elo, attempts |
| `generated_question` | same fields as `questions.json` |
| `llm_cache` | key, response_json, created_at |
| `app_clock` | offset_days |

## 7. Learner model

All functions here are pure and take the current time as an argument.

### 7.1 Mastery update

The model is Bayesian Knowledge Tracing. Each concept starts at mastery 0.3, and the result is limited to the range 0.01 to 0.99.

- Correct: `p' = p(1-s) / (p(1-s) + (1-p)g)`
- Wrong: `p' = ps / (ps + (1-p)(1-g))`
- Learning, when `T` is above 0: `p'' = p' + (1-p')T`

| Answer | `error_type` | Slip `s` | Guess `g` | Learn `T` | Result from p = 0.5 |
|---|---|---|---|---|---|
| Correct | `none` | 0.1 | 0.2 | 0.1 | 0.836 |
| Correct | `misconception`, `gap` | 0.1 | 0.9 | 0 | 0.500 |
| Correct | `slip`, `unclear` | 0.1 | 0.5 | 0 | 0.643 |
| Wrong | `misconception`, `gap`, `none`, `unclear` | 0.1 | 0.2 | 0 | 0.111 |
| Wrong | `slip` | 0.6 | 0.2 | 0 | 0.429 |

These values are test cases. A correct answer with flawed reasoning leaves mastery unchanged, and a careless slip barely lowers it.

### 7.2 Graph propagation

A mastery change of `d` moves prerequisites by up to two links:

- Positive `d`: multiply by 0.3 per link.
- Negative `d`: multiply by 0.1 per link.

Propagation doesn't change a prerequisite's review schedule, and it can't push mastery outside the allowed range.

### 7.3 Misconception update

Each misconception starts at probability 0.05. The confidence tap sets a multiplier `k`: 1.0 for "Sure" and 0.6 for "Not sure".

| Event | Update |
|---|---|
| Diagnosis names `m` with confidence `c` of at least 0.6 | `p += (1-p) * 0.7 * c * k` |
| Selected option maps to `m`, and the diagnosis didn't name `m` | `p += (1-p) * 0.2 * k` |
| Correct answer with `error_type: none` on a question with an option mapping to `m` | `p *= 0.5` |

| Status | Rule |
|---|---|
| `inactive` | Starting status; `p` below 0.2 and never `active` |
| `candidate` | `p` at least 0.2 and below 0.5 |
| `active` | `p` at least 0.5 |
| `resolved` | Was `active`, now `p` below 0.2 (two sound answers from about 0.65) |

Diagnoses with `c` below 0.6 are treated as `unclear`, so the tutor asks another question instead of asserting a misconception. If a resolved misconception's probability reaches 0.5 again, it returns to `active`.

### 7.4 Spaced repetition

- Recall is `R = exp(-days_since_practice / S)`, and a review is due when `R` falls below 0.85.
- Concept stability `S` starts at 2 days, and every answer on the concept restarts its recall clock. A correct answer with `error_type: none` doubles `S`. An `error_type` of `slip` or `unclear` leaves it unchanged. Any other answer halves it, with a minimum of 1 day.
- Displayed mastery is `mastery * (0.5 + 0.5R)`, so it fades over time without reaching zero.
- A resolved misconception starts with `S` of 3 days and uses the same recall rule for rechecks. A sound answer on a recheck doubles `S`. A failed recheck updates its probability under section 7.3.
- Reviews always use a question the student hasn't seen recently, never the same question again.
- "Jump 7 days" adds to `app_clock.offset_days`, and all time-based calculations use the offset clock.

### 7.5 Difficulty calibration

The Elo scale gives each student a rating starting at 1500 and sets each question from its prior:

| `difficulty_prior` | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| Starting Elo | 1200 | 1350 | 1500 | 1650 | 1800 |

- Expected success is `E = 1 / (1 + 10^((d - a) / 400))`.
- After each answer, with `K = 32`, the student gains `K(actual - E)` and the question loses the same amount.
- The dashboard flags a question when its Elo differs from its starting value by 150 or more and it has at least 10 attempts.

## 8. Choosing the next question

Code applies the first rule that returns a question, and excludes the student's 3 most recently served questions.

| Priority | Situation | Selection |
|---|---|---|
| 1 | `pinned_question_id` is set | That question, then clear the pin |
| 2 | `diagnostic_complete` is false | Section 8.1; set it to true after the eighth answer |
| 3 | Any misconception with `p` at least 0.2 | Section 8.2 |
| 4 | Any review due | Lowest recall first, resolved misconceptions before concepts |
| 5 | Any Electricity concept with questions is below mastery 0.7 | Weakest such concept whose prerequisites are all at least 0.5; otherwise its weakest prerequisite that has questions |
| 6 | Nothing needed | Return "all caught up" |

**Tie-breaks,** applied in order: expected success closest to 0.6, then question ID, so results are repeatable. If a chosen concept has no unseen question, the agent tries one live generation for numeric concepts (section 9.2), then falls back to the question the student saw longest ago.

### 8.1 Diagnostic test

Choose the Electricity concept with mastery closest to 0.5 that has an available question. Break ties in favour of the concept with the most concepts depending on it.

### 8.2 Separating explanations

Take the top two misconceptions by probability, then score each available question:

```text
score = sum of p(m) for each top-two m that has an option in the question
        + 0.5 if both have options and those options differ
```

The highest score wins, and questions scoring 0 are skipped. The trace records the explanations, their probabilities and the reason for the choice.

## 9. LLM use

| Setting | Value |
|---|---|
| Model | `qwen3.5:9b` |
| `think` | `False`, unless the Step 9 comparison favours turning it on |
| `temperature` | 0 |
| `num_ctx` | 8192 |
| `keep_alive` | -1 |
| `format` | The Pydantic JSON schema, also included in the prompt |
| Timeout | 30 seconds |
| Invalid replies | Validate with Pydantic, retry up to two times |
| Cache | `llm_cache`, keyed by a hash of the model, prompt and schema |

Measured so far: 4/4 on the demo cases at about 1.2 seconds each with thinking off, using an earlier schema without `error_type`. The new schema must pass the same cases before other work starts on the agent.

### 9.1 Diagnosis

Inputs are the question, selected option, correctness, the student's reasoning and the Electricity catalogue. Code then applies these checks:

- `evidence_quote` must appear in the student's text. Otherwise it is cleared and the confidence is capped at 0.5.
- `misconception_id` is required when `error_type` is `misconception`, and is otherwise cleared.
- Empty reasoning skips the LLM and is treated as `unclear`.
- Student text is untrusted. It is wrapped in clear delimiters and the prompt says to treat it only as data. The schema limits what a reply can do.

### 9.2 Question generation

The LLM writes a numeric question and picks a calculation from a fixed list. Code computes the answer.

- **Allowed calculations (`agent/solvers.py`):** `ohm_current`, `ohm_voltage`, `ohm_resistance`, `series_resistance`, `parallel_resistance`, `power`, `energy`.
- **Reply format:** stem, calculation name, numeric arguments, options and difficulty prior. Each wrong option names a misconception ID or null.

A question is rejected unless all of these hold:

- The calculation's result matches exactly one option, within 1%.
- All options have different values.
- Every misconception ID is in the catalogue.

Rejected questions are retried up to two times. `scripts/pregenerate.py` builds the pool ahead of time. Conceptual questions are always hand-written and reviewed.

### 9.3 Lesson plan

The LLM drafts a short plan for the most common active misconception: a title, a board demonstration and a check question chosen from the question bank. It is generated once and cached.

## 12. Simulated class and evaluation

### Simulated class (`scripts/seed_class.py`)

- 30 students, each with 0 to 2 hidden misconceptions, and a fixed random seed of 42.
- Each student gets 12 to 15 scripted answers.
- When a question has an option for a hidden misconception, the student picks it 80% of the time. Otherwise, the student answers correctly with the Elo expected probability.
- The script builds the diagnosis from the hidden truth, makes no LLM calls and passes every answer through the real engine.

This data shows how the dashboard works. It isn't evidence that diagnosis works.

### Evaluation (`scripts/evaluate.py`)

- 40 labelled reasoning samples with messy wording, checked by a person: 10 for tuning prompts and 30 held out for the reported result.
- Measures `error_type` accuracy, misconception accuracy and time per diagnosis on the 30 held-out samples.
- Runs with thinking on and off. Keep thinking off unless turning it on is clearly more accurate and the response time still works for a demo.
- Saves results to `eval/results.json`.
- The pitch must describe these as written test cases, not real student data.

## 13. Error handling

| Failure | Behaviour |
|---|---|
| Ollama down or timed out, or invalid after retries | Save the answer, update mastery from the option alone using `unclear`, return `diagnosis_status: failed`, and show a small notice |
| Generated question rejected | Retry, then use the fallback in section 8 |
| Student has no available question | Reuse the question seen longest ago, or return "all caught up" |
| Malformed content at startup | Stop with an error naming the file and item |
| Demo state changed during rehearsal | `POST /api/demo/reset` |
